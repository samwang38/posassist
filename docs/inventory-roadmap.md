# 庫存與調撥後續升級

目前試用版本為 `1.6.0-preview.4`。找貨沿用 STORESUM 原生搜尋與勾選，點原生查詢區「庫存工具」才開啟視窗，每次依原生目前勾選取代商品；比較表以商品為列、門市為欄，僅顯示現有庫存；不保留自製搜尋入口或獨立調撥清單。先完成新版在士林的登入、庫存與操作回歸，再安排以下升級。V1.1–V1.4 是功能階段，實際版號沿用專案規則。

後續原生建單與網站銜接需重新確認現場操作方式，不恢復已取消的前置調撥清單流程。

| 階段 | 使用者能力 | 必須完成的驗收 |
|---|---|---|
| V1.1 原生建單輔助 | 將出入庫門市、多筆商品帶入原生申請表，由店員確認；成功後取得單號 | 原生權限、數量與單位驗證有效；取消不建單；結果不明不得重複建立；單號與草稿品項核對一致 |
| V1.2 備貨建議 | 接入近期實銷、已確認待入庫、客訂及保留量，分品類設定目標庫存 | 需求與在途不重複計算；區分新品、缺貨造成的低銷量及慢銷品；可解釋建議量的來源與日期 |
| V1.3 多店調撥與網站銜接 | 找較少來源店的拆分方案，按來源店產生草稿，以 ERP 單號連結需求管理網站 | 分配總量一致；失敗可補登且不重複；保留客訂群組各自數量及隨單備貨，沿用網站到貨核對方式 |
| V1.4 範圍與協作 | SAS 分體系查詢、區域與偏好店、跨次草稿保存、多人處理 | 公司與倉庫邊界明確；草稿版本衝突可辨識；跨體系流程驗證後才開放 |

## 原生建單輔助的前置工作

先檢查 `INVTRNRN` 實際使用的表單模型、明細新增動作、數量／單位與倉庫驗證、批號序號及必要欄位。使用可取消的測試情境追蹤原生建立、儲存、取消及回傳單號；不能把第一版的「開啟原生申請」視為已完成原生寫入驗證。再設計草稿與原生表單的差異預覽，以及未明結果的查證／人工接手流程。

## 備貨建議的資料契約

第一版的比較差額不能直接改名為建議補貨量。需先定義實銷期間、退貨、贈品、缺貨天數、有效在途單據狀態與客訂保留的關聯鍵；為每個來源保留時間與完整性狀態。資料不足時顯示依據不足，不以零值代替。

## 多店與網站銜接的資料契約

每份來源店草稿有自己的識別碼及 ERP 單號；網站失敗可以相同識別碼補登。調撥總量、各客訂群組分配與隨單備貨必須相加一致，不由工具靜默平均分配。原始品項數量保留為調撥總量，各群組採獨立數量，延續現有網站的群組與到貨核對方式。

跨公司調撥、自動發信、自動確認到貨另行規劃。第一版不新增網站 API 或資料庫 migration；以上階段未納入此次安裝包。
